# Content document v2: pages, collections, and prose

The content document was a single `sections[]` array: one page, no `<head>`, no chrome. That is the whole shape a tenant site could take. The first tenant's own site is eleven pages — an index, five generated project pages, a studio page, a contact page, a colophon and a 404 — so the CMS could reproduce its home page and nothing else.

Decision: the document gains a version and becomes `{ site, pages[], collections{} }`. A page is a path, its discovery metadata and an ordered list of sections. A collection is a path template plus an ordered list of entries the builder fans out into a detail page each. Site settings carry the chrome and the metadata a page falls back to. `schemaVersion` discriminates, `parseContentDocument` upgrades v1 on read, and every write emits the current version.

Field vocabulary gains two primitives: `prose`, an ordered array of paragraphs, and `slug`, the URL segment an entry contributes to its path. `prose` is the constrained long-prose type [ADR-0001](./0001-editor-model.md) anticipated and [`fieldTypes.ts`](../../packages/schema/src/content/fieldTypes.ts) reserved an ADR for.

I chose this because the alternative to collections is a hand-made page per project, which drifts from its index the first time someone edits one and not the other — and because a client adding a sixth project should not need a deploy. That is the difference between a CMS and a site with an editor bolted on.

## Alternatives considered

- **One page per project, no collections** — rejected. Nothing relates the index to the detail pages, so prev/next has no source of order and the index is a second copy of the same content, maintained by hand. It also puts route creation behind the same UI as content editing for a set of pages that are structurally identical.
- **Collections as a separate table** — rejected for now. Entries in their own rows scale past what one JSONB document holds and would allow per-entry concurrent editing. But every piece of machinery around content — the immutable snapshot, the content hash, the idempotency key, the SSE preview channel, rollback — is built on the document being one value. Splitting entries out means touching all of it. At five projects the single document is not the constraint; revisit above roughly two hundred entries or when two people need to edit different entries at once.
- **Markdown for prose** — rejected. It buys inline emphasis and inline links at the cost of a parser, a sanitiser and an HTML-bearing string in a pipeline that currently has none. Paragraphs render as `<p>` each, the template styles them, and there is nothing to escape. Adding emphasis later means a richer element inside the same array, not a different field.
- **A constrained Tiptap editor** — rejected for now, and it remains the answer if a tenant needs real rich text. It is an editor bundle, a JSON node schema, a renderer and a sanitiser: the right cost for authoring long-form editorial, too much for project descriptions.
- **`sections[]` kept, with page as a section field** — rejected. It makes page membership a property of a section rather than sections a property of a page, so "the sections on this page, in order" becomes a filter-and-sort rather than an array, and the uniqueness rule has nowhere to live.

## Consequences

- **The v1 branch is permanent.** `content_versions` snapshots are immutable, `rollbackToVersion` accepts any version whose status is `built`, and the reaper keeps ten per workspace plus the live one. A rollback can therefore select a v1 snapshot and must render it without a rebuild. Deleting the v1 reader turns that rollback into a failed build. The document schema only ever grows readers ([`docs/migrations.md`](../migrations.md)).
- **Rolling back across the boundary produces a one-page site.** That is correct — the snapshot is what was published — but it looks like data loss on a button that reads as "undo".
- **Every read upgrades, every write emits v2.** Both database read boundaries do it (`getDraftDocument`, `getVersionSnapshot`, and the dashboard's draft services) rather than the callers, because the publish gate hashes what it stores and the preview route hashes what it renders. Hashing opposite sides of the upgrade makes every save emit a hash that never matches the render, and the iframe reload-loops with no error logged anywhere.
- **`contentHash` changes for every document.** Expect every workspace to show "unpublished changes" after deploy, and the first publish to miss the idempotency key and rebuild content nobody edited.
- **Site settings are storable while blank, and that is load-bearing.** v1 has nowhere to carry a site name, so the upgrade seeds it empty rather than inventing one from the workspace slug — a title tag nobody chose is worse than a prompt. Requiring it in the storage envelope would mean an upgraded document could be produced and then never read back: it would parse once, save, and fail every load after that, with the row already written. The publish gate refuses the empty value instead. This is [ADR-0007](./0007-preview-architecture.md)'s loose-save / strict-publish split applied one level up.
- **Pages and entries carry `enabled`, added now rather than later.** The publish gate validates strictly, so without it one half-written page or one unfinished project refuses to publish the entire site — every finished page included. Retrofitting it would be a second migration.
- **Section types are unique per page, not per document.** That is the point of pages, and it makes every `section.type ===` lookup across a flat list a cross-page mutation. The editor's mutators are page-scoped, and section form state is keyed by page as well as type — the form seeds from its props at mount and is uncontrolled after, so a page switch that reused a mounted card would show the previous page's values and immediately stream them upward over the new page's.
- **Media references must keep the `mediaId` key at any depth.** The orphaned-media reaper finds live references by scanning serialized JSON for `"mediaId":"<uuid>"`, which is depth-independent and so survives the extra nesting — but a shape that stored a media id under any other key would make every image it references look unreferenced, and they are deleted with their R2 variants after seven days.
- **The `mediaRef` detector became a subset check.** It matched an exact key set, so the first field added to `mediaRef` would fall through every branch and throw at module load — inside the dashboard's template registry, which builds every spec eagerly, taking the whole editor down over a field nobody had used yet.
- **The schema is ahead of the surfaces.** The document holds many pages; the builder still emits one, the preview renders one, and the editor edits one. Routes, `<head>` and the page switcher follow. This ADR is the shape; shipping it in one change would have meant reviewing the migration and the rendering together.

**Amendment: collections render, and the two derivations they need have one home.** The schema half of this ADR shipped ahead of the surfaces, as its last consequence said it would. The builder now fans out a detail page per entry, an index section lists them, and the editor edits one.

Two derivations turned out to be needed by three consumers each, and letting each compute its own was the mistake worth designing out. `livingEntries` resolves each entry's path and drops the parked ones: the build emits no page for a disabled entry, an index must not link to one, and prev/next must not walk through one. The third is the one that would have been missed — a neighbour pointing at a parked entry is a 404 reachable only by clicking "next project", which is exactly the link nobody tests. `withNeighbors` is Norven's helper minus its `order` field, because array position is already the order; a separate sort key is a second source of truth that drifts the moment someone reorders in one place. Its wraparound is kept so the sequence has no dead end, with one exception: a collection of one would have both links pointing at the page they are on, and a "next project" that reloads the same project reads as broken rather than as a cycle of one.

**Pages and entries share one route, deliberately.** They occupy the same path space, so a single `getStaticPaths` is the only place "one route per path" can be checked. Two route files would each be internally consistent and collide silently in R2, where the second upload wins and the loser reads as a page that simply did not publish. Both ends now refuse it — the publish gate compares entry paths against page paths and names the entry, and the builder asserts the same invariant, because a snapshot can reach it without passing the gate through a hand-run build or a rollback.

**A collection is rendered by one component, not a dispatch.** An entry is one shape repeated rather than an arbitrary composition, so `CollectionRenderer` pairs a detail component with a `summarize` function instead of a map keyed by type. `summarize` exists because `<head>` is not the component's to write: a detail page needs a title, the only honest source is the entry's own fields, and only the template can read them. Without it every project page would have titled itself with the site name until an author retyped each title into per-entry SEO. The same function labels prev/next, so a link and the page it points at cannot disagree about a project's name.

Everything that reads an entry outside the strict publish gate reads it leniently. Entries are savable half-written, so the index skips one it cannot narrow rather than throwing — an index that refused to render because a draft entry is incomplete would take every finished project down with it, in the preview, while the author is still typing.

**The field vocabulary needed three more kinds**, and the pattern is now established enough to name. `year` is a number and `status` an enum, because the detail page's `CreativeWork` JSON-LD needs a real `dateCreated` and a real name for the work's kind — a search engine cannot split "Residence · 2023 · Built", and writing a parser for one would be a taxonomy the CMS is pretending not to have. A third kind, `group`, was added for any object that is not a `mediaRef` or a `link`, so a grouped field is never again a change to the describer.

That failure mode has now happened three times: a union inside an array of links, a boolean on page SEO, and this pair. Each threw while the dashboard's registry was still evaluating, which takes the whole editor down and surfaces as a missing Publish button in an end-to-end run — a symptom three packages from its cause. `packages/template-norven/src/manifest.test.ts` now asserts every section and every entry shape describes cleanly, so the next one fails in `pnpm verify` naming the field and the schema type.
