# Repo and runtime topology: pnpm monorepo, two runtimes (dashboard + api)

Plinth is one pnpm + Turborepo monorepo containing two deployable applications (`apps/dashboard`, `apps/api`) and six shared packages (`schema`, `db`, `renderer`, `template-norven`, `ui`, `auth`). The dashboard is Next.js App Router; the api is a Hono Node service. They deploy independently to separate Fly.io machines (both with `auto_stop_machines = "stop"` for the portfolio-budget posture), communicate over HMAC-signed internal HTTP with end-to-end type inference via Hono RPC, and share types via in-workspace package imports rather than published npm releases. I chose this because the shared contracts that span the apps — `schema` (Zod), `db` (Drizzle), `renderer` (React) — are the load-bearing properties of the system, and the only model where drift between them is structurally impossible is when they resolve to one module at compile time. The two-runtime split is a separate decision: long-lived connections (SSE per [ADR-0007](./0007-preview-architecture.md)), CPU-heavy endpoints (Sharp per [ADR-0006](./0006-media-pipeline.md)), and background workers (Inngest per [ADR-0003](./0003-publish-pipeline.md)) deserve a runtime that does not share request capacity with the UI render path. Hono specifically was chosen over Fastify because the api's workload skews toward SSE channels, edge-runtime-friendly handlers, and RPC-style contracts with the dashboard — all of which Hono offers as first-class primitives rather than plugin layers.

## Considered options

- **Monorepo + two runtimes (`apps/dashboard` Next.js + `apps/api` Hono)** (chosen) — pnpm workspaces + Turborepo, atomic schema changes across both apps, independent Fly.io deploys (`auto_stop_machines` for budget), separate process per workload class. Shared contracts via packages, end-to-end type inference between apps via Hono RPC (`hc<AppType>(...)` from the dashboard against the api's exported route types).
- **Monorepo + Fastify api + tRPC layer** — rejected. Workable but redundant for this stack: tRPC is a second type system stacked on top of Fastify's own route typing, and the `@trpc/server` Fastify adapter lags the Express/Next adapters in maintenance. Hono provides the same end-to-end RPC inference natively with no extra package, and its SSE primitive matches the preview-channel pattern in [ADR-0007](./0007-preview-architecture.md) more cleanly than Fastify's stream adapter. The tRPC pattern would have been correct if we were sticking with Fastify; switching to Hono subsumes it.
- **Monorepo + single runtime (Next.js as backend)** — rejected. The Sharp upload endpoint (libvips, ~600 ms per 4000×3000 photo) and the SSE preview channel both compete with UI request handling on the same Node process; one slow upload degrades the dashboard's TTFB. Vercel Edge runtimes also disqualify libvips entirely, and Vercel Node functions impose cold-start latency on the upload endpoint. Splitting workloads to a dedicated api process is the conservative move; the monorepo decision is independent of it.
- **Polyrepo, separate FE/BE repos with published shared packages** — rejected. The shared contracts span both apps and change frequently during the build; npm-publish coordination + Changesets adds ceremony without buying isolation that two separate Fly.io machines already provide. Each schema change becomes a three-PR dance (schema publish → dashboard bump → api bump) where a missed bump produces a runtime drift bug.
- **Polyrepo with codegen (OpenAPI / protobuf for type sharing)** — rejected. Drift becomes a runtime-detected bug class instead of a compile-time impossible class. Codegen is the right answer when languages differ (Go BE + TS FE, for example) — both apps here are TypeScript, so the codegen layer is pure overhead taxing every schema change with a regeneration step and a generated-file commit that pollutes diffs.
- **Single repo, single Next.js app, deploy on Vercel** — rejected. Couples to Vercel runtime constraints; Edge functions disqualify Sharp; long SSE connections fight Vercel's request-duration limits and require workarounds; couples the deploy cadence of UI and backend to one release cycle.
- **Polyglot stack (Go backend, TypeScript frontend)** — rejected. The CPU-heavy thing in Plinth is Sharp's call to libvips C++; rewriting the caller in Go saves nothing because libvips does the work regardless of caller language. Plinth's workload (HTTP CRUD + Sharp + Astro builds + SSE) runs on Node without throughput concerns. Polyglot would add a build toolchain, a type-sharing layer (protobuf / OpenAPI), and per-language CI lanes — for no measurable payoff at this workload class.

## Consequences

- **Repo layout** is `apps/{dashboard,api}` + `packages/{schema,db,renderer,template-norven,ui,auth}` + `docs/adr/`. Each app has its own `package.json`, `tsconfig.json` (extends a root base), `Dockerfile`, and Fly.io app. Each shared package emits compiled JS + `.d.ts` for IDE speed; consumers import from the package name, not relative paths.
- **The two apps are independent processes on independent machines.** `apps/dashboard` runs Next.js on one Fly.io app; `apps/api` runs Hono on another. Both apps deploy with `auto_stop_machines = "stop"` and `min_machines_running = 0` so the machines scale to zero on idle and wake on the next request — the lever that keeps the portfolio bill at ~$0-2/mo on quiet days. A spike in upload traffic does not degrade dashboard rendering, and vice versa. Independent autoscaling rules per app.
- **Communication uses Hono RPC over HMAC-signed internal HTTP.** The dashboard imports the api's root Hono app as a type-only import — `import type { AppType } from "@plinth/api"` — and instantiates a typed client via `hc<AppType>(INTERNAL_API_URL, { headers: hmacHeaders })`. Every request and response is inferred at compile time from the api's route definitions; renaming a field on a Hono route surfaces as a typecheck failure on the dashboard call site without any codegen step. The HMAC envelope (shared secret in the `auth` package, rotating via Fly.io secrets) authenticates internal calls; user-scoped calls additionally forward the session cookie (same root domain, attaches automatically). The shared `auth` middleware validates both shapes on the api side, so the same session check runs on both runtimes via one import.
- **Database is shared (one Postgres) but each app owns its own connection pool.** The `db` package exports a client factory; the dashboard and api each instantiate one pool sized to their own concurrency profile. The factory enforces the `workspace_id` GUC pattern from [ADR-0002](./0002-tenant-isolation.md) — a query cannot be issued without the GUC having been set, so RLS applies on both runtimes identically.
- **Turborepo orchestrates everything.** `turbo run lint test build --filter=...[origin/main]` runs only the affected app on each PR; cache hits make repeat CI fast. Full pipeline locally is `pnpm verify` (mirroring Norven), which fans out to per-app lint/test/build via Turbo.
- **Each app has its own Dockerfile and CI deploy job.** Selective deploys via path-filter triggers on GitHub Actions: a dashboard-only PR deploys only the dashboard; a `packages/schema` change rebuilds and redeploys both. Norven's OIDC + scoped-IAM posture applies per-app where the deploy target supports it (Fly.io uses scoped deploy tokens issued via OIDC).
- **Selective CI matters because the cost story matters.** Without selective builds, a one-line dashboard typo would trigger api tests + builds + lints. Turbo's affected-graph + remote cache cuts CI minutes by ~60% in practice on a five-package monorepo of this shape.
- **Server code cannot leak into the client bundle.** `import "server-only"` markers in `packages/db`, `packages/auth`, and any server-only module fail the Next.js build if a client component imports them. An ESLint rule (`no-restricted-imports`) belt-and-suspenders the marker. CI fails if either gate fails.
- **Env config is per-app via Zod-typed schemas.** Each app exports `env.ts` that parses `process.env` against a per-app Zod schema; an unset required var fails the boot. Public vars (`NEXT_PUBLIC_*` on the dashboard) live in a separate Zod schema with a different exported name, so a server var cannot accidentally be referenced from the client by typo.
- **Secrets are per-app on Fly.io.** Dashboard knows: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `INTERNAL_API_HMAC_SECRET`, `SENTRY_DSN_DASHBOARD`. Api additionally knows: `STRIPE_WEBHOOK_SECRET`, `CLOUDFLARE_API_TOKEN`, `INNGEST_SIGNING_KEY`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `SENTRY_DSN_API`. A leaked dashboard secret cannot impersonate api webhook signatures or write to R2; a leaked api secret cannot decode dashboard sessions on its own. The HMAC envelope on the dashboard ↔ api channel is the only secret shared between both runtimes, and rotating it requires redeploying both apps in lockstep — documented as the one coupling point.
- **Telemetry posture is Sentry-only.** Each app sends to its own Sentry project (`plinth-dashboard`, `plinth-api`) for errors and basic performance traces; cross-app traces propagate via standard W3C `traceparent` headers on internal HTTP calls, so a publish trace spans dashboard click → api enqueue → Inngest job → R2 upload as one connected story in Sentry's performance view. Honeycomb was considered for richer tracing but rejected at this scale — the overlap with Sentry's performance product is too large to justify two vendors, the second one's free tier still costs setup time, and the portfolio budget posture (≤$5/mo) leaves no headroom for a Honeycomb paid tier later. If observability needs ever outgrow Sentry's free tier (5k errors/mo, 50 perf spans/mo), Honeycomb is the documented upgrade path; for now, one product covers both signals.
- **CodeQL, `pnpm audit`, and `dependency-review` scan the whole monorepo in one CI workflow** — same posture as Norven, scaled to the workspace. Renovate is configured at repo root with grouped patch updates per workspace.
- **`docs/adr/` lives at the repo root, not per-app.** ADRs describe cross-cutting decisions; co-locating with one app would imply scope they do not have.
- **Trade-off: a single bad commit can break both deployable builds.** Mitigation is identical to Norven — required CI before merge, branch protection on `main`, small PRs. The blast radius of a bad PR is the same as polyrepo if both apps changed; smaller than polyrepo if only one app changed (because there is only one CI to wait on, not N).
- **Trade-off: contributors need pnpm + Turborepo familiarity.** Acceptable — both are mainstream, well-documented, and the cognitive load is one-time. The `CONTRIBUTING.md` covers the workflow explicitly.
- **Trade-off accepted: the monorepo grows over time.** The first time a third deployable is needed (a CDN worker service, a CLI tool, an admin app), it lives in `apps/`; no repo split. Repo size is bounded by Plinth's domain, not by team count.
- **Polyrepo migration is reversible.** Each `packages/*` is npm-publishable in shape (named scope, public API surface, compiled output); each `apps/*` is self-contained. The cost of monorepo is the reversible option. The cost of polyrepo (coordinated history, multi-repo refactor, codegen retrofit) is not. Choosing monorepo first leaves the door open; choosing polyrepo first closes it.
