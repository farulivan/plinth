# Backend architecture: module-per-domain, three-rule layering, no DI ceremony

The api service is organized as one folder per domain (`modules/media`, `modules/publish`, `modules/domains`, `modules/preview`), with three layering rules: routes validate input and delegate; services hold business logic as plain functions; adapters wrap external SDKs in one file each. No repository interfaces, no DI container, no application-layer abstractions over Drizzle. The dashboard's Server Actions in `apps/dashboard/server/` follow the same module shape, so a domain's logic is one folder regardless of which runtime calls it. I chose this because it matches the abstraction level the workload actually needs — HTTP CRUD with five external APIs and one ORM — and because every layer beyond "route → service → adapter" pays its cost in ceremony without earning testability or clarity at this scale.

## Considered options

- **Module-per-domain, three-rule layering** (chosen) — routes → service → adapter; Drizzle imported directly in services; no DI container; one folder per domain with colocated tests. Scales the `src/lib/*` pattern Norven already uses, applied to a Node backend.
- **Hexagonal / ports-and-adapters** — rejected. Wins when infrastructure swap is a real use case (DB engines, message brokers). Plinth's DB is Postgres-via-Drizzle for the foreseeable life of the project; the swap-ability promise costs interfaces + mapping layers for zero payoff.
- **Clean Architecture (entity → usecase → controller → framework)** — rejected. Four indirection layers and a mapping step between each. The ceremony is for codebases where multiple delivery mechanisms (HTTP, gRPC, CLI, scheduled job) share one domain. Plinth has two callers (Hono routes + Inngest functions) and one domain — the abstraction is unnecessary and reads as overengineering.
- **DDD with aggregates + value objects** — rejected. The domain isn't rich enough to earn aggregates. A `Draft` is a JSON blob validated against a Zod schema; wrapping it in an aggregate root with invariants is theater. DDD pays off when the domain language is the product; Plinth's product is the editor + the published site, not the content model's algebra.
- **Repository pattern with interfaces** — rejected. Drizzle's typed query builder is the interface; adding a thin `MediaRepository` over it adds a file per entity without removing a dependency. The "we might swap ORMs" hypothesis is the same one the hexagonal pattern serves, and the answer is the same: we will not.
- **Vertical slice architecture (feature folder owns everything)** — rejected. Vertical slices win when features are independent and change frequently in isolation. Plinth's domains share services across features (media is used by drafts and by publish; publish is used by HTTP and by Inngest). Horizontal modules with one service per domain match the actual reuse pattern; vertical slices would duplicate.
- **No structure — everything in route files** — rejected. Works for week 1, painful at week 8 when business logic needs to be called from an Inngest function (a separate caller from HTTP). The first feature that needs reuse forces the extraction; doing it from day one costs nothing and prevents the messy first refactor.

## Consequences

- **Three rules, total, enforced by ESLint:**
  1. Routes import services and middleware; never adapters, never Drizzle, never external SDKs.
  2. Services import adapters, `@plinth/db`, `@plinth/schema`, and other services; never `req`/`res`, never Hono types.
  3. Adapters import only third-party SDKs and `@plinth/schema`; never services, never `@plinth/db`.

  A `no-restricted-imports` rule makes the graph machine-checkable at lint time. A future reader can know what any file is allowed to depend on without reading the import block.

- **Routes are thin.** Validate input with a Zod schema (often re-imported from `@plinth/schema`), call the relevant service, format the response. Routes that exceed ~50 lines almost always have logic that belongs in a service; the threshold is a soft refactor signal, not a hard rule.
- **Services are plain functions, not classes.** They accept typed inputs and return typed outputs. They never see `req`/`res`. Tests instantiate the service with mocked adapters (via `vi.mock` or direct factory injection) and assert pure input/output behavior. The "no classes" default is because class state encourages stateful services that fight horizontal scaling — function services are stateless on construction.
- **Adapters wrap external SDKs in one file each:** `storage.ts` (S3), `cloudflare.ts` (CF API), `stripe.ts`, `resend.ts`. The service calls `storage.putObject(...)`, never `s3Client.send(new PutObjectCommand(...))`. The wrapper is one indirection step with no interface — if the SDK changes shape, one file updates; if we ever swapped S3 for R2, one file updates. This is the only adapter pattern that earns its keep.
- **Drizzle queries live inside services**, sometimes pulled into a per-module `db.ts` helper when two services in the same module repeat the same query. There is no global `repositories/` folder. The query shape is right next to the business logic that needs it.
- **Inngest functions consume the same services that HTTP routes do.** A publish workflow service is called from `routes/inngest.ts` (the Inngest event receiver) and could be called from a future internal trigger or a CLI without modification. This is the practical justification for extracting services from routes — two callers force the abstraction.
- **Cross-cutting infrastructure lives in `lib/`** (env, logger, db client factory, tracing init). Not domain. A service may import from `lib/`, but `lib/` may never import from `modules/` — same dependency rule, enforced by lint.
- **Middleware wraps routes; never touches services.** Auth validation, RLS GUC injection ([ADR-0002](./0002-tenant-isolation.md)), rate limiting ([ADR-0003](./0003-publish-pipeline.md)), error formatting all live in `middleware/` and compose at route registration time. A service called from an Inngest function gets the GUC from a different code path (the job runner per [ADR-0003](./0003-publish-pipeline.md)) — the middleware is HTTP-layer specific; services do not depend on the middleware existing.
- **Each module folder is self-contained:** `service.ts`, `service.test.ts`, optional adapter files, optional `db.ts` helper. Adding a domain area is: new folder under `modules/`, new service, wire up the route, add a test. Linear cost per domain, no graph editing of a god config.
- **The dashboard mirrors the structure under `apps/dashboard/server/`** — Server Actions live in `server/actions/{domain}.ts` and delegate to `server/services/{domain}/service.ts`. Same three rules, same dependency direction. A developer who learns the api layout can navigate the dashboard server side without recalibration.
- **Shared packages are imported across both apps without duplication.** `@plinth/schema`, `@plinth/db`, `@plinth/auth` are the contracts; dashboard and api both consume them. There is no parallel definition of a domain type — adding a field to a section schema in `packages/schema` propagates through TypeScript to every service and route that consumes it. Drift is caught at compile time, per [ADR-0008](./0008-repo-and-runtime-topology.md).
- **Trade-off: services couple tightly to Drizzle.** The "swap ORM" optionality is sacrificed. Accepted because that swap has near-zero probability and the cost of the abstraction (interfaces + mappers per entity) is paid every day.
- **Trade-off: no DI container means test setup uses module mocking or factory-injected adapters.** Worse than DI for highly complex factories; for adapters with 1-3 methods each, simpler. A future migration to `tsyringe` or `awilix` does not change service code, only test setup, so deferral is cheap.
- **Trade-off: module-per-domain assumes domains are stable.** If a domain (e.g., `media`) later splits into `images` + `videos` + `assets` with distinct rules, the split is mechanical (move files, rename imports) — not a re-architecture. Acceptable for foreseeable scope.
