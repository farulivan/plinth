# Publish pipeline: Inngest queue, per-tenant Astro build, content-addressed snapshots

Publish is a queued job. When a tenant clicks Publish, the dashboard validates the draft against the current template schema, snapshots the draft into an immutable `content_versions` row, and enqueues an Inngest job whose only side effects are an Astro build against the snapshot, an upload of the build output to `s3://plinth-sites/tenants/{workspace_id}/v{N}/`, and an atomic update of the tenant's `current_version_id`. The web request returns once the snapshot exists; everything else is asynchronous, retryable, and observable. I chose this because the failure mode under load is "publish queues up, lands eventually" rather than "publish blocks the web request, times out, and leaves the tenant guessing"; because per-tenant content-addressed paths mean the CDN never needs an explicit cache invalidation; and because reusing Astro as the build engine means the renderer that proved itself on Norven is the same renderer doing tenant work.

## Considered options

- **Inngest queue + per-tenant Astro build + content-addressed snapshots** (chosen) — durable queue, retry and idempotency built in, observable via Inngest's dashboard. Content snapshots decouple the build from the editor's live state, so a tenant editing during a build cannot corrupt the in-flight version. Atomic pointer swap means rollback is one row update.
- **Direct invocation from the web request** — rejected. A build that takes 30 seconds blocks the request; a build that times out leaves the dashboard in an unknown state and the user re-clicking; no retry without bespoke code; no observability beyond logs.
- **Postgres `LISTEN/NOTIFY` + a hand-rolled worker** — rejected. The queue is exactly the kind of code I do not want to own. The questions an attentive reviewer asks — retry policy, visibility timeout, DLQ — are answered by Inngest out of the box; hand-rolling would answer each one badly and I would have to defend the answers.
- **Per-tenant GitHub Actions runs** — rejected. This is the deploy pipeline pattern from Norven, but a tenant publishing five times in a minute would burn five workflow runs (and on a free tier exhaust the runner pool), plus the security model breaks down: GitHub Actions needs repo write access to commit content, and committing tenant content to a repo gives every tenant a path to every other tenant's content via git history.
- **Edge rendering (Cloudflare Worker fetches content from DB on every request)** — rejected. Loses the static-build cost ceiling that makes the Norven hosting model cheap; every request becomes a DB hit instead of a CDN hit. Could revisit at a scale where rebuild-on-edit beats cache-on-publish; not at portfolio/SMB scale.
- **ISR-style on-demand revalidation** — rejected. Requires a dynamic origin that can rebuild a page on cache miss, which means abandoning the S3 + Cloudflare hosting story from Norven for a Next runtime origin. The cost shape changes.
- **Per-tenant git repo + git-push deploys (Cloudflare Pages style)** — rejected. Adds a git layer between dashboard and CDN that the dashboard would have to manage credentials for; the tenant never sees the repo, so the git layer is pure overhead.

## Consequences

- **Publish is two distinct write events.** First, the web request validates the draft and inserts a row into `content_versions(id, workspace_id, snapshot jsonb, created_at, created_by)` then enqueues an Inngest event with `{version_id}`. The web request returns at this point and the UI shows "Publishing…". Second, the Inngest job runs the build and updates the workspace's `current_version_id` on success. A user closing the tab between the two does not break anything; the job runs to completion regardless.
- **Snapshots are immutable.** Once `content_versions.snapshot` is written, it never changes. A tenant editing during a build is editing the `content_drafts` row, not the snapshot — the in-flight build cannot see those edits, and the next publish picks them up as a new snapshot. The dashboard surfaces "you have unpublished changes" when the draft hash differs from the current version's hash.
- **Per-tenant storage layout** is `s3://plinth-sites/tenants/{workspace_id}/v{N}/index.html` and friends. A Cloudflare Worker fronts the bucket and rewrites `tenant-host → tenants/{workspace_id}/v{current_version_id}/`. The Worker reads `current_version_id` from KV (synced from Postgres on every promote) so the routing decision is sub-millisecond. The KV-vs-DB choice saves one outbound hop per request — worth it for the read pattern.
- **Atomic pointer swap means rollback is a row update, not a re-deploy.** The build artifact for `v(N-1)` still exists in S3 (until the retention reaper deletes it), so rolling back is `UPDATE workspaces SET current_version_id = $previous`. Rollback latency = KV sync time, on the order of seconds.
- **Build artifact retention is bounded.** A reaper Inngest job runs daily and deletes versions older than the most recent 10 per tenant. Documented in `docs/operations.md` as part of the cost story; the reaper itself is the only operational toil this pattern introduces.
- **Idempotency keys on the publish API.** Every publish API call carries an `Idempotency-Key` header; the snapshot insert is keyed on `(workspace_id, idempotency_key)` with a unique constraint. A retried publish from a flaky network returns the existing snapshot, not a duplicate. The idempotency table is itself RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **Concurrency: one in-flight publish per tenant.** Inngest concurrency group `publish:{workspace_id}` serializes within a tenant; cross-tenant publishes run in parallel up to the global Inngest concurrency cap. If a second publish arrives while the first is running, the second queues behind it (not cancelled, not coalesced); both produce distinct snapshots and both run to completion. Coalescing rapid publishes is a future optimization but adds a state machine the MVP does not need.
- **Failure means the build fails and the version is not promoted.** The user sees an error with a short summary and a "Retry" button that re-enqueues the same `version_id`. Inngest's automatic retries (3 attempts with exponential backoff) cover transient failures invisibly; persistent failures land in an Inngest DLQ that emits an alert.
- **Per-tenant rate cap: 20 publishes per day per workspace,** enforced by an Upstash Redis counter. Beyond the cap, the API returns 429 with `Retry-After`; the UI surfaces "you've published 20 times today — next available at HH:MM". The cap is the cost cover for free-tier tenants and a flag for misbehaving editors.
- **Build time budget: 60 seconds.** Norven's full build is ~30 s; per-tenant builds typically have fewer images (no portfolio backlog). A build exceeding 60 s fires a Honeycomb alert; chronic exceedance is the trigger to look at image processing or content size, not to raise the budget.
- **Audit log records every publish event:** `workspace_id`, `actor_user_id`, `version_id`, snapshot hash, build duration, outcome. Reading the audit log is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **The build is the only place a privileged role runs.** It sets `SET LOCAL app.workspace_id` from the job payload before any tenant DB read, then drops privileges back. The discipline is documented as the job function's first three lines so a reader sees it without scrolling.
- **The renderer is `packages/renderer` (see [ADR-0007](./0007-preview-architecture.md)),** shared between the build and the preview route. The build is `astro build` invoked against the snapshot mounted as content; the preview is a Next route that server-renders the same components. The same module on both sides means production output and preview output are the same DOM, the same a11y tree, and the same Vitest tests cover both.
- **Trade-off accepted: HTML edge caching is deferred to a Cloudflare Cache Rule, not the default.** Same posture as Norven's deployment ADR — instant deploy propagation beats edge cache hits at this scale. The shape of the publish pipeline is unaffected; the cache decision is a config toggle layered on top.
