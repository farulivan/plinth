# Preview: single renderer, draft snapshot via SSR, iframe transport with SSE-driven reloads

The preview is the production renderer rendering the draft. The dashboard mounts an iframe pointing at `/preview/[draft_id]`, a Next App Router route that server-renders the same React components the published Astro build uses, reading content directly from the `content_drafts` row (RLS-scoped to the tenant). When the editor form saves a debounced patch to the draft, the server emits a Server-Sent Event on the draft's channel; the iframe receives it and reloads. There is one renderer module, two trigger points, and no drift between what the editor sees and what publish ships. I chose this because the parity guarantee is the load-bearing property — drift between preview and production is a class of bug that erodes tenant trust in a CMS, and the only way to make drift impossible is to share the rendering code path; because reload-on-update is enough for an SMB CMS (sub-second is the threshold, not sub-frame); and because the iframe is same-origin, so the session cookie does the auth without a token bridge.

## Considered options

- **Iframe + same-origin SSR preview route + SSE reload on draft change** (chosen) — single renderer, session-cookie auth, sub-second update path, no hot-patch infrastructure.
- **Hot-reload via DOM patching (Webflow-style)** — rejected. Patching requires the renderer to expose stable patch boundaries (component IDs that survive across renders), which doubles the renderer's complexity. Drift between "patched DOM after 20 edits" and "freshly server-rendered DOM" is the exact failure mode visual builders have bugs about; not a fight worth picking when the parity property is the whole point.
- **Separate preview renderer (light HTML stub, no styling)** — rejected. The whole pitch is "what you see is what publishes"; a stub preview is a worse UX than no preview because it gives the tenant false confidence in a render that does not match production.
- **Cross-origin preview at the tenant subdomain** — rejected. CORS for SSE, session bridging via signed tokens, cookie scoping headaches across the dashboard and the tenant host. Same-origin makes all three problems vanish; the URL shape `/preview/[draft_id]` on the dashboard origin is enough.
- **Static snapshot regeneration on save** — rejected. Latency is wrong: a 5-second build per keystroke debounce is intolerable; a 30-second build per save is worse than no preview. The build is for publish, not for preview.
- **WebSocket transport instead of SSE** — rejected. SSE is one-way (server → iframe), which matches the access pattern exactly: the editor saves via plain HTTP, not over the socket. WebSocket would need a multiplexed protocol and a reconnect strategy; SSE has browser-native reconnect for free.

## Consequences

- **The renderer is `packages/renderer`** — a set of typed React components that take a content shape (Zod-inferred type from `packages/schema`) and render the page. Production build: `astro build` against a per-tenant content snapshot mounts the components into Astro pages, processes images, and emits static HTML. Preview: a Next App Router route mounts the same components against draft content, server-renders, and streams HTML to the iframe. Same components on both sides; the substrate differs, the output does not.
- **The renderer is template-aware, not tenant-aware.** A template ships as its own package (`packages/template-norven` is the first; `packages/template-photo-portfolio` is a candidate second) implementing the same render interface. The active template per workspace lives on the `workspaces` row; the dashboard, the preview route, and the publish job all read it from one column.
- **Same-origin iframe means the session cookie attaches automatically.** The preview route reads the session, checks the user has access to the draft's workspace, sets the `workspace_id` GUC per [ADR-0002](./0002-tenant-isolation.md), and renders. No token bridge, no cross-origin auth, no special-case headers — the route is just an authenticated Next page that happens to mount the renderer instead of dashboard chrome.
- **The update loop is debounce → write → SSE → reload.** Form input fires a 500 ms debounce; the debounce calls a Server Action that writes the patch to `content_drafts`; the server emits an SSE event `{type: "draft-updated", draft_id, hash}` on the channel `draft:{draft_id}`; the iframe receives the event and reloads `/preview/[draft_id]`. The `hash` field lets the iframe skip a reload if the patch did not change the rendered shape (same hash as last render).
- **Reload-on-update, not patch.** The full re-render takes ~80 ms on a Fly.io / Railway-class runtime for a Norven-shape page; the visible reload is masked by an instant fade. Drift impossible; complexity bounded.
- **Image fields resolve identically in preview and production.** Both modes read CDN URLs from the media library per [ADR-0006](./0006-media-pipeline.md). The renderer abstracts the resolution via a `resolveImageUrl()` helper that reads `import.meta.env.PREVIEW_MODE` — currently identity in both modes, kept as a seam for a future signed-URL gate on private previews.
- **The motion runtime is loaded in preview, but reduced-motion is forced.** The renderer sets `data-prefers-reduced-motion="reduce"` on `<html>` in preview mode so Lenis cannot fight the dashboard's scroll handling and ScrollTrigger cannot pin inside an iframe. Reuses Norven's reduced-motion guard verbatim.
- **Empty optional fields render as preview-only placeholders** (`Photo placeholder — eyebrow`) so the editor sees the structural shape and can decide whether to fill the field. Norven's `<Frame>` already has this affordance for missing photos; reused verbatim.
- **Validation surfaces inline in the editor form, not in the iframe.** A draft that fails schema validation does not render; the iframe shows "Fix the validation errors to see your preview". This is the right place for errors — the editor can act on them, the iframe can only display them, so the iframe defers.
- **Mobile preview is a width toggle on the iframe container** (`375 / 768 / 1280 / 100%`), not a separate device emulator. The renderer is responsive already; matching the viewport is enough to see the right breakpoint, and a "device frame" UI is dashboard chrome to defer.
- **The preview route is excluded from the production sitemap** and gated behind authentication, so search engines cannot crawl it and a leaked URL still requires a valid session cookie. The route's metadata sets `noindex, nofollow` regardless.
- **The Inngest publish job (see [ADR-0003](./0003-publish-pipeline.md)) consumes the same renderer module via `astro build`.** Vitest unit tests for the renderer (Norven-style, pure-module surface) cover both paths because there is only one renderer to test. Visual regression (Chromatic / Playwright snapshots) runs against the preview route in CI on every PR; a regression caught in preview is a regression caught in production at the same time.
- **SSE reconnect is browser-native** — `EventSource` reconnects on disconnect with the last seen event ID, so a flaky network produces a brief preview lag, not a stale preview. The server keeps an in-memory ring buffer of the last 20 events per channel (Redis-backed if horizontally scaled) so a reconnect catches up without a re-fetch.
- **The preview SSR route has its own performance budget** distinct from production: TTFB ≤ 200 ms, full render ≤ 300 ms. Slower than that and the reload becomes perceptible; faster than that and the debounce dominates the latency budget. Honeycomb traces span debounce → Server Action → DB write → SSE emit → iframe reload so the whole loop is observable.
- **Trade-off accepted: the dashboard runtime is not a thin Next-on-Vercel default** — it has to support an SSR'd route that renders arbitrary template components against arbitrary content. Fly.io or Railway is the deploy target; the deploy ADR will pick one explicitly. Documented separately.
- **Trade-off accepted: a slow renderer hurts preview latency directly.** This is intentional — it surfaces renderer slowness during development, not after a tenant ships a slow site. A Norven-shape page that exceeds the 300 ms preview budget would also miss Norven's LCP budget in production; both fail the same way for the same reason.
