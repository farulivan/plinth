# Product strategy: MIT code, ARR brand, hosted service as the commercial surface

Plinth is open-source code under MIT and a closed-source operations layer that runs a hosted commercial service. The git repository (apps, packages, ADRs, docs, CI workflows) is MIT-licensed; the brand (the Plinth name, marks, marketing prose), reference template demo content, and the operations layer (deploy configs, account IDs, customer data) are private. Public commercial use of the brand is not licensed; deployments of the codebase under different brands are permitted. I chose this because the codebase serves two readings — portfolio piece for hiring filters, and foundation of a small freelance practice deploying Plinth-class sites — and the licensing model that supports both is the one Norven already uses: open code, owned brand, paid operations.

## Considered options

- **MIT code + ARR brand + hosted operations** (chosen) — code visible for portfolio and learning; brand reserved as a commercial asset; hosted service is the paid product. Same model as Cal.com, Plausible, Ghost, Documenso, and Norven itself.
- **Fully open including brand (MIT for everything)** — rejected. The Plinth brand and demo content are commercial assets; a competitor could spin up a Plinth-branded clone and dilute the freelance offering with no legal recourse. The brand reservation is one paragraph in `LICENSE.md`, not a code change — cheap protection.
- **BSL / Elastic v2 / SSPL (source-available, restricted commercial use)** — rejected. Some international hiring filters (FAANG-tier OSS review boards in particular) refuse to evaluate candidates whose public repos use non-OSI licenses. The portfolio surface is the primary purpose of the public code; license hygiene matters more than per-clone competitive protection at this scale.
- **AGPL** — rejected. Technically OSI-compatible but forces any client customizing their site to open-source the customization. Kills freelance offerings where clients want private branding/copy without publishing forks. Also creates OSS-review-board friction in larger enterprises.
- **Closed-source private repo** — rejected. Loses the portfolio purpose entirely. The whole point is the code being readable end-to-end.
- **Open core (core MIT + premium modules paid)** — deferred. Reasonable future model when paid templates or enterprise integrations exist; not the right MVP shape because there are no premium modules to gate yet. The MIT-everything posture is easy to narrow later (move a template to a private repo); narrowing first and broadening later is a harder direction.

## Consequences

- **`LICENSE.md` mirrors Norven's three-section structure:** Code (MIT), Brand and copy (All Rights Reserved), Reference content / images (separate notes). The mirroring is deliberate — anyone reading the two licenses sees one consistent author.
- **All code in `apps/`, `packages/`, `scripts/`, `.github/workflows/`, `docs/` is MIT.** Read, fork for personal use, copy patterns into other projects — all permitted. Forks running under a different brand are permitted; forks running under the Plinth brand are not.
- **The Plinth name, logo, marketing prose, and dashboard chrome copy** are reserved. A fork can run the codebase under a different brand; it cannot run the Plinth brand. The brand reservation is enforced through trademark norms (use without permission is misrepresentation), not technical measures.
- **Reference template demo content (the Norven fictional studio) is reserved.** Forks can use the codebase to build their own sites with their own content; they cannot use Norven's photographs (Unsplash-licensed; license follows the photos) or copy.
- **Operations layer lives outside this repository.** Fly.io app names, Cloudflare account IDs, KV namespace IDs, Postgres connection strings, Stripe live keys, R2 bucket names, per-client deployment configs all live in a separate private repository or as repository secrets only. Public CI workflows reference these via repository variables and secrets, never inline in workflow YAML.
- **Tenant data never enters the repository.** Content lives in Postgres; media lives in S3 / R2; audit logs live in Postgres. Per [ADR-0002](./0002-tenant-isolation.md). The repo is code; tenant data is operations.
- **Secret scanning runs at pre-commit and in CI.** Lefthook runs `gitleaks` on staged files; CI runs `gitleaks detect` against the diff. A leaked Stripe live key, a CF API token, or a Resend key is a six-month problem — the cheapest mitigation is making it impossible for a hand to slip.
- **README explicitly explains the dual-use model.** A reader (hiring filter, freelance prospect, contributor) lands on the same understanding: open-source code, hosted commercial service, contact for either path. The transparency is the freelance hook — the open-source posture removes lock-in fear and converts conservative buyers.
- **Norven is positioned as tenant #0 of the hosted Plinth service.** The Norven repository remains independent and standalone; the hosted Plinth at norven.farulivan.com is what the public sees. The dogfood narrative reinforces both portfolios — Norven proves the template, Plinth proves the system.
- **`SECURITY.md` ships at parity with Norven's** — disclosure policy, contact, expected response window. Public code is auditable by security researchers, which is a net positive; the disclosure path makes that auditability productive rather than disruptive.
- **`CONTRIBUTING.md` sets expectations** — bug reports welcome, security reports through `SECURITY.md`, feature PRs accepted case by case. Feature work that diverges from the freelance roadmap may be declined; the contributor's fork remains MIT and they can run it themselves. This is fair under MIT and standard among single-maintainer open-source projects.
- **Open-source code is a feature for freelance clients, not a liability.** It reduces lock-in fear: "you can leave anytime, the code is MIT, hire any developer to take over." This makes the sale easier — conservative buyers in particular convert better with an explicit exit path documented in the contract.
- **License selection is reviewed if any of these change:** (a) a competitor begins commercializing under the Plinth brand at scale (legal action, not license change), (b) hiring filter feedback explicitly flags MIT as a problem (extremely unlikely), (c) the freelance product reaches a scale where open-core gating becomes financially material (move a specific template package to a paid private repo; rest stays MIT).
- **Trade-off accepted: a determined competitor can clone the codebase and offer a competing service under their own brand.** Possible but unlikely at MVP scale — the customer profile that would hire a competing GitHub clone over a known operator is not the freelance target customer anyway. The moat is brand + trust + operations + execution, not source secrecy.
