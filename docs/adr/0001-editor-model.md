# Editor model: typed fields per section, not a visual canvas

The editor is field-based. Each section template declares a Zod schema of fields; the dashboard renders a form for those fields; the renderer consumes the validated data. No drag-drop canvas, no free placement, no arbitrary HTML, no rich-text-as-default. Tenants pick which sections to include and in what order — everything else is typed content. I chose this because one engineer can ship it in a quarter, because the typed schema is the editing surface (not arbitrary pixel placement), and because the product is a typed CMS for one template shape, not a visual builder.

## Considered options

- **Field-based editor against a shared Zod schema** (chosen) — react-hook-form + Zod, one section = one form. `packages/schema` exports the Zod schemas consumed by the editor (for form generation), the API (for validation), and the renderer (for typed content). A schema change propagates through TypeScript compile errors to every consumer.
- **Visual canvas (Webflow / Framer-style)** — rejected. The editor is the product in a visual canvas, and the editor UX is what Webflow has spent eight years and tens of millions polishing. A single-person team will ship a worse canvas in a quarter than tenants would get for free elsewhere. The product positioning here is "typed template + simple CMS"; tenants who need a canvas belong on Webflow.
- **Markdown + frontmatter (Sanity-minimal / git-CMS style)** — rejected for non-technical tenants. An architect or photographer opening the dashboard once a quarter to swap a hero photo needs a labelled image field with a preview, not a YAML block. Markdown is a future option inside a long-prose section type, not the editor model.
- **Block-based composable editor (Notion-style, Tiptap-driven)** — rejected. Half the complexity of a visual canvas without the freedom payoff. The substrate (ProseMirror / Tiptap) is itself a project larger than the rest of this CMS, and locks the renderer into rich-text JSON that's harder to type-check, harder to migrate, and harder to render server-side identically every time.

## Consequences

- **Schema is the product.** `packages/schema` is the load-bearing module; the dashboard, the renderer, the API, and the test suite all import from it. A new section type is a Zod schema + a renderer component + a form-control mapping — three files, linear cost. Adding a field is one edit and a backfill plan.
- **Section toggle + reorder is the only structural freedom.** A tenant turns sections on or off and reorders them; the renderer composes the page in that order. Nothing else moves. This is the only structural decision the tenant ever makes about layout.
- **A11y is owned by the renderer template, not the editor's output.** A tenant cannot ship inaccessible markup by accident, because they don't author markup — they fill fields whose rendering is fixed by the template. Reuses Norven's axe-clean budget verbatim.
- **Schema migration becomes the operational problem.** Adding a field to template v2 means every v1 tenant's content gets a default for it — the additive-with-default migration pattern is the only safe shape until a second template ships. Document this in a migration playbook (`docs/migrations.md`) before the second template lands; otherwise the second template is the regression.
- **No rich-text by default.** A long-prose section type may eventually need it, and that section will introduce a constrained Tiptap or markdown-with-remark renderer — but only when a tenant actually needs prose. The default Norven-shape template uses display headings and short body copy and does not need rich-text editing.
- **Image fields go through the media library, not per-section uploads.** One upload path, one Sharp pipeline, one CDN URL shape, one library UI. An image field's value is a media reference, not a URL.
- **Editor latency stays cheap.** A field-based editor renders sub-100 ms; a canvas editor has to model an entire DOM and commit changes through a synthetic layout engine. The trade-off here is not ambition — it is choosing the model whose performance ceiling matches the budget I can hit.
- **Out of scope: tenants who need free placement.** They use Webflow or hire a developer for a bespoke build. The renderer enforces layout so content stays on-brand inside the template constraints — broadening the scope to free placement is the feature that quietly takes a quarter and never lands.
