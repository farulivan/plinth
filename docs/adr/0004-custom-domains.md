# Custom domains: Cloudflare for SaaS, automated TLS, hostname lookup at the edge

A tenant binds their own hostname to their workspace through Cloudflare for SaaS. The tenant adds a CNAME pointing at Plinth's fallback hostname, the dashboard registers the custom hostname via Cloudflare's API, Cloudflare provisions and renews the TLS certificate automatically, and the existing Cloudflare Worker that fronts the tenant origin (see [ADR-0003](./0003-publish-pipeline.md)) routes by hostname — looking up `workspace_id` from a KV namespace synced from Postgres — into the same `s3://plinth-sites/tenants/{workspace_id}/v{current_version_id}/` path that subdomain tenants use. I chose Cloudflare for SaaS because it solves multi-tenant TLS, edge routing, and apex-domain support in one piece of infrastructure I already operate in Norven, and because the alternative (orchestrating ACME challenges, running Caddy or Traefik, terminating TLS on the application runtime) is the kind of operational depth that pays off only at a scale where the per-hostname cost of Cloudflare for SaaS exceeds the engineering and operational cost of running it myself.

## Considered options

- **Cloudflare for SaaS Custom Hostnames** (chosen) — automated cert provisioning (HTTP-01 and DNS-01), automatic renewals, hostname-to-origin routing handled by Cloudflare, apex-domain support via CNAME flattening or fallback A records. Reuses Cloudflare, which already fronts every Plinth tenant.
- **Caddy or Traefik on the dashboard runtime with on-demand TLS via Let's Encrypt** — rejected for MVP. Zero per-hostname cost and full ownership of TLS termination, but introduces a stateful TLS layer the app runtime must own, a certificate store that must persist and survive runtime restarts, and ACME rate limits to manage at scale. Worth it if per-hostname Cloudflare cost ever exceeds ops cost (probably above 200 hostnames); documented as a migration path.
- **AWS CloudFront + ACM (cert per distribution)** — rejected. ACM certs require `us-east-1`; CloudFront distributions multiply per hostname; the routing layer would have to be Lambda@Edge, which is a different programming model than the Cloudflare Worker already handling tenant routing. Adds an AWS surface that Norven's hosting ADR intentionally minimized.
- **Vercel Domains API** — rejected. Couples the project to Vercel; the dashboard's preview architecture (see [ADR-0007](./0007-preview-architecture.md)) is deploy-target-agnostic and the deploy ADR will pick Fly.io or Railway specifically to avoid Vercel lock-in. Custom domains living on Vercel would re-introduce that coupling.
- **Subdomain only — no custom domains** — rejected as MVP scope. The product positioning requires `studio.com` as the live URL; `studio.plinth.app` is the kind of branding compromise that loses a freelance conversation on first contact.

## Consequences

- **The `custom_domains` table** is `(id uuid pk, workspace_id uuid references workspaces, hostname text unique, cf_custom_hostname_id text, status enum, created_at, verified_at)`. RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **`hostname unique` at the DB level prevents two tenants from binding the same domain** even by collusion. Cloudflare for SaaS would also reject the second registration via its own uniqueness, but enforcing at the DB level fails the attempt with a clear error before any CF API call — better error message, no wasted API quota.
- **A Cloudflare Worker (`worker-router`) reads a KV namespace** mapping `hostname → {workspace_id, current_version_id}`. On every request, the Worker looks up the `Host` header, fetches the mapping, and rewrites the origin URL to the per-tenant path. KV reads are sub-millisecond at the edge; the same path covers subdomain and custom-domain tenants with no branching.
- **KV sync is asynchronous, eventual.** A Postgres trigger on `workspaces.current_version_id` and on `custom_domains` writes to an Inngest queue; an Inngest function consumes the queue and updates KV via the Cloudflare API. Convergence on the order of seconds — acceptable because the failure mode is "tenant sees old version for a few seconds after publish", never "tenant sees wrong tenant's content" (the Worker fails closed on a KV miss).
- **Hostname onboarding flow** is wholly UI-driven: dashboard surfaces the CNAME instructions (`CNAME studio.com → tenant-fallback.plinth.farulivan.com`); a polled check against Cloudflare's API tracks verification state (`pending_validation` → `pending_issuance` → `active`); UI surfaces the current state with a "what to do next" hint. Tenant never copies an API key, never opens a Cloudflare dashboard.
- **Apex domain support** uses Cloudflare for SaaS's fallback A records, exposed in the UI alongside the CNAME instructions. The tenant's registrar (and whether their DNS is on Cloudflare) determines which path they take; documenting both keeps the path navigable for tenants on Route 53, Namecheap, GoDaddy, or Cloudflare itself.
- **Hostname removal is reversible for 7 days.** Tenant clicks Remove → dashboard calls the CF API to delete the custom hostname and marks the row as `removed` → reaper deletes the row after the cooldown. The cooldown protects against accidental removal during a domain dispute or offboarding negotiation; the audit log captures the removal event regardless.
- **Cost model.** Cloudflare for SaaS Custom Hostnames cost $0.10/active hostname/month on Free above the included quota; sustained 100 tenants = $10/mo on top of CF Pro. Documented as the cost ceiling for this layer; the Caddy migration is the lever if growth makes it material. The AWS Budget ceiling pattern from Norven applies here too — a CF spend alert at $25/mo bounds the cost surprise.
- **Per-workspace hostname quota** is the SKU differentiator. Free tier capped at 1 hostname, paid tier at 5, enterprise unlimited. Defensible against domain-squatting and tied to the Stripe metadata for the workspace; the quota check is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **TLS posture matches Norven verbatim.** Cloudflare terminates at edge; CF → origin is HTTPS to the dashboard runtime (Fly.io / Railway terminate TLS) and HTTP to S3 for static asset pulls (same content-is-public reasoning as Norven's ADR-0003). The audit trail for that decision sits in `norven/docs/adr/0003-static-hosting-pipeline.md`; this ADR inherits it rather than restating.
- **Audit log records every domain binding event** (`add`, `verify`, `remove`, `failure`) with `workspace_id`, `actor_user_id`, `hostname`, `cf_response`. Reading the audit log is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md). A failed verification with a misconfigured DNS record produces an audit row plus a UI banner, not a silent failure.
- **Cloudflare for SaaS is the single load-bearing third-party** in the live-serving path. If the Custom Hostnames API is unavailable for new hostnames, existing hostnames continue serving because the CF edge cache, DNS layer, and Worker are independent of the Custom Hostnames API. Migration to Caddy + ACME is the documented contingency; the Worker would change but the rest of the pipeline does not.
- **Trade-off accepted: the dashboard runtime is permanently aware of Cloudflare-specific concepts** — KV namespaces, Workers, the Custom Hostnames API. The project is not cloud-agnostic. The trade is "deepen Cloudflare practice in exchange for one piece of infrastructure that does five jobs"; the README is explicit about it.
