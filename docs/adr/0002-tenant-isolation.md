# Tenant isolation: `workspace_id` on every row, enforced by Postgres RLS

Every tenant-owned row carries a `workspace_id` column referencing `workspaces(id)`. Postgres Row-Level Security policies restrict every query to the workspace named by a session-level GUC (`SET LOCAL app.workspace_id`), set by request middleware inside a per-request transaction. Isolation is enforced by the database engine, not by application query authors. A single missing `WHERE workspace_id = ?` in a future query cannot leak rows across tenants — RLS denies the read regardless. I chose this because the isolation invariant is too important to rest on every future engineer (including future-me) remembering to filter, because the operational story is one database / one schema / one migration set, and because the failure mode under a missing GUC is "queries return empty" rather than "queries return another tenant's data".

## Considered options

- **Single DB + `workspace_id` + Postgres RLS** (chosen) — one schema, one connection pool, isolation enforced at the engine. Cheap at this scale; isolation provable by a cross-tenant probe test that runs in CI. Standard Supabase pattern, familiar to anyone who has worked on multi-tenant Postgres.
- **Single DB + `workspace_id`, application-only filtering** — rejected. Means every query author must remember to filter on `workspace_id` on every read, write, and join. Tests can only check what is written today; they cannot enforce what a future query will look like. One missed `.where()` is a tenant-data leak; RLS makes that single failure mode impossible. The convenience win (no policy maintenance) is not worth the risk profile.
- **Database per tenant** — rejected. Strongest isolation, prohibitive operations: N migrations per release, N connection pools, N backup-and-restore stories, N monitoring dashboards. Worthwhile under genuine compliance pressure (HIPAA, PCI) at hundreds of tenants; overkill at zero-to-hundreds for a content CMS without sensitive data.
- **Schema per tenant** — rejected. Same migration overhead as DB-per-tenant without the strong-isolation payoff. Cross-schema joins are awkward; analytics queries need a `UNION ALL` across N schemas. Strictly worse than both alternatives.

## Consequences

- **Every tenant-owned table has `workspace_id uuid not null references workspaces(id) on delete cascade`.** No exceptions. A table without `workspace_id` is either `workspaces` itself, `users`, or a global lookup (e.g. country codes) — and that distinction is documented in the table comment.
- **Every tenant-owned table has an RLS policy** with the same predicate for `SELECT / UPDATE / DELETE`: `USING (workspace_id = NULLIF(current_setting('app.workspace_id', true), '')::uuid)` — the `NULLIF` because Postgres reverts a custom GUC to `''` (not NULL) at session level after any transaction has set it, and a bare `''::uuid` cast errors instead of returning empty. `INSERT` uses a `WITH CHECK` clause forcing `workspace_id = current_setting(...)`, so a malicious insert cannot write a row owned by another workspace even with a hand-crafted payload.
- **Request middleware opens a transaction and issues `SET LOCAL app.workspace_id = $1` before any tenant-scoped query.** The Drizzle client is request-scoped, not module-scoped, so a leaked client between requests cannot carry a stale GUC. Outside a transaction, `current_setting('app.workspace_id', true)` returns NULL and every RLS policy denies — queries return empty, which is the safe failure mode. A failed `SET LOCAL` means no rows are visible; it never means another tenant's rows are visible.
- **Background jobs run under a privileged role with RLS bypassed**, but each job accepts a `workspace_id` parameter and issues the `SET LOCAL` inside its own transaction before touching tenant data. The job runner is the only place RLS is intentionally bypassed, and the bypass is documented per-job. Job code reviews include the GUC discipline as a checklist item.
- **Cross-tenant probe test runs in CI on every PR.** Authenticated as tenant A, the test constructs a query asking for tenant B's rows by hard-coded ID — and asserts an empty result. The probe runs against a real Postgres instance (testcontainers), not a mock. A regression in policy authoring fails this test before review.
- **Audit log is itself a tenant-owned table** with `workspace_id` and `actor_user_id` on every event. Reading the audit log is RLS-scoped: a workspace admin sees their own audit trail and no others.
- **Custom-domain bindings are tenant-owned.** A `custom_domains(workspace_id, hostname unique)` table with RLS means an attacker cannot bind their workspace to a competitor's hostname — the insert fails the `WITH CHECK` clause if `workspace_id` does not match the GUC. The `hostname unique` constraint prevents two tenants binding the same hostname even by collusion.
- **Migrations apply globally.** No per-tenant migration scripts, no fan-out runbook. Forward-compatible migrations (add column with default, deploy, backfill, drop default later) are the only shape that is safe; a destructive migration is a coordinated multi-step release. Document the expand/contract playbook in `docs/migrations.md` so this is a habit, not a heroic event.
- **Analytics queries are first-class RLS citizens.** When workspace A's dashboard renders a tenant-level chart, the same request middleware sets the GUC; the same RLS policy filters the data. There is no "admin query layer" that bypasses RLS — except inside Inngest jobs that explicitly bind a workspace before reading.
- **Trade-off accepted: migration coupling.** All tenants run the same schema at the same version. There is no "tenant A on schema v3, tenant B on schema v4" path. For a CMS, that is the right call — keeping the renderer monomorphic against schema version is more valuable than per-tenant migration staging. Revisit if a single enterprise tenant ever needs schema isolation; the answer then is to fork that tenant onto database-per-tenant, not to retrofit per-tenant migrations on the shared DB.

**Amendment:** the expand/contract playbook this ADR asked for is written, at [`docs/migrations.md`](../migrations.md), along with the step that makes global migrations safe for this specific schema: a new tenant table is added to `tenantTables` in `packages/db/src/rls.ts` and its policy statements land in the same migration. The drift guard in `rls.test.ts` turns a table registered in code but missing from the SQL into a `verify` failure — which is the only reason "every tenant table has a policy" is an invariant rather than an intention.
