# Authentication: Better Auth, database-backed sessions, magic-link as the primary login

Authentication uses Better Auth with server-managed sessions stored as rows in the `sessions` table via its first-class Drizzle adapter. The primary login path is email magic-link delivered via Resend through Better Auth's magic-link plugin; OAuth (Google) is a second-class option enabled by the same library's social-provider plugin after the magic-link flow is solid. Session lifetime is 30 days with a sliding extension window; tokens are opaque, server-validated, and revocable by deleting the row. I chose Better Auth because the session model is explicit and database-shaped rather than hidden behind a third-party SDK, because the library is actively maintained where Lucia v3 was placed on a sunset path in March 2024, because magic-link removes the worst customer-support surface (forgotten passwords), and because rolling sessions in a single Postgres table interact cleanly with the `workspace_id` GUC pattern from [ADR-0002](./0002-tenant-isolation.md).

## Considered options

- **Better Auth + Drizzle adapter + magic-link plugin** (chosen) — sessions are rows I can audit, revoke, and reason about. The library is small enough to read end-to-end and actively maintained. Email is the only credential, so there are no password resets to support, and the security surface drops to "is your email account secure" — which it would have been anyway, because email controls password reset on every other system. The magic-link plugin ships with single-use, time-bound tokens out of the box; the social plugin extends to OAuth without restructuring anything.
- **Lucia v3** — rejected. Lucia v3 had the exact shape we wanted (thin library, explicit DB-row sessions, no JWT hides) and was the first choice when this ADR was drafted. The Lucia maintainer announced deprecation in March 2024 with a sunset path that boils down to "use Oslo and build the session layer yourself" — adopting Lucia v3 now would mean inheriting an unmaintained foundation on the most security-sensitive part of the system. Better Auth fills the same shape with current maintenance and a richer plugin ecosystem (magic-link, OAuth, two-factor, organizations) without the hand-rolled assembly Oslo would require.
- **Oslo + hand-rolled session layer** — rejected. This is the path Lucia's maintainer points to: use Oslo's primitives (crypto, JWT helpers, OAuth flows) and write the `sessions` table + middleware + magic-link flow yourself. Defensible for a team with auth specialists; the carry cost for a solo maintainer is too high — every Better Auth release of a bug fix or new plugin would be a manual port to a hand-rolled equivalent. The resulting shape would be near-identical to what Better Auth ships out of the box, so choosing Oslo means owning that surface area for no architectural difference.
- **Auth.js (NextAuth) with JWT sessions** — rejected. JWT sessions mean revocation requires a denylist (defeating the JWT-statelessness pitch) or short-lived tokens (worse UX); DB sessions in Auth.js are an option but the library has more surface area and the magic-link adapter is less polished than Better Auth's. The underlying reason: the auth library should be small enough to audit the entire surface in an afternoon, and Better Auth hits that bar where Auth.js does not.
- **Clerk / Auth0 / Supabase Auth (managed)** — rejected. Faster to ship, but the auth model becomes a vendor black box. Questions like "explain your session lifetime, your revocation story, and your CSRF posture" turn into "Clerk handles it" — a portfolio piece whose point is showing the model loses the point when the model is owned by a vendor.
- **Fully hand-rolled (no library)** — rejected. Library code is the only code I want to not re-implement. The boring bugs (token entropy, timing-safe comparisons, session fixation, replay) are exactly what a maintained auth library gets right; reinventing them is engineering hubris.
- **OAuth-only (Google / GitHub) as primary** — rejected as primary. Locks out users who do not want to bind a workspace identity to a personal Google account, and a fresh studio workspace is exactly the case where a shared email alias (`hello@studio.com`) is the right identity. Magic-link is the lower-friction default; OAuth ships as a second path once the magic-link flow is solid.

## Consequences

- **The `sessions` table is small and read on every request.** Better Auth's Drizzle adapter generates the base columns (`id text primary key, user_id uuid not null references users on delete cascade, token text unique not null, expires_at timestamptz not null, ip_address text, user_agent text, created_at timestamptz default now(), updated_at timestamptz default now()`); Plinth extends the schema with one custom column — `active_workspace_id uuid references workspaces` — wired via Better Auth's `additionalFields` config. RLS is not applied to `sessions` — sessions are scoped by `user_id` directly, validated by the auth middleware before any tenant code runs. The middleware then looks up the user's workspace memberships, picks the active one (from `active_workspace_id`), and issues the `workspace_id` GUC for that request per [ADR-0002](./0002-tenant-isolation.md).
- **Magic-link tokens are single-use, 15-minute expiry, opaque, stored in the `verifications` table.** Better Auth's magic-link plugin persists the token row at request time and consumes it on click in a transaction (`SELECT ... FOR UPDATE` then DELETE), so a captured link cannot be replayed by a network observer and cannot be consumed twice from a duplicated email. Token entropy, hashing, and timing-safe comparison are the plugin's responsibility; the application code only calls `auth.api.signInMagicLink({ email })` and trusts the library on the cryptographic boring parts.
- **Session cookies are `HttpOnly`, `Secure`, `SameSite=Lax`,** scoped to the apex hostname so per-tenant subdomains share the session. Custom domains require their own per-domain session; that is documented separately in [ADR-0004](./0004-custom-domains.md) when the custom-domain flow lands.
- **Sliding expiry, daily reaper.** A session within 15 days of expiry is extended on use. Sessions older than 30 days are deleted by a daily Inngest job. Revocation is one DELETE on the row; the next request fails the auth middleware lookup and lands on `/login`.
- **CSRF is mitigated by `SameSite=Lax`** on the session cookie plus an explicit origin check in the Server Action wrapper. Mutating Server Actions verify the `Origin` (or `Sec-Fetch-Site`) header matches the configured hostname. The origin check lives in one wrapper function so a future reader can find it; a Server Action that does not go through the wrapper is a review-block.
- **Email delivery uses Resend with a per-user rate limit** (5 magic-links per 15 minutes, 20 per day) implemented in middleware against Upstash Redis. The UI always shows "we sent a link; check your spam" — the block is server-side so timing the response does not reveal whether the email exists. One Redis dependency accepted as a trade-off; documented here so a future "remove Redis to simplify" PR has the context.
- **OAuth is additive, not retrofit.** Better Auth's social-provider plugin uses a separate `accounts` table (`id, user_id, provider_id, account_id, access_token, refresh_token, id_token, expires_at, scope, created_at`) joined to `users` rather than a column on `users` itself, so the schema for OAuth lands in the initial migration as an empty table and stays empty until the Google plugin is enabled. Adding OAuth later is one config block in `packages/auth` plus the env vars — no destructive migration, no backfill, no `users` shape change.
- **Audit log records every successful login, every failed magic-link consumption, every session deletion, every workspace switch.** Reading the audit log is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **Logout is a real action.** It deletes the session row. "Sign out everywhere" deletes all sessions for the user — useful when offboarding a workspace member or when a user signs out of a lost laptop from a different device.
- **Multi-workspace switching is a session-level state, not a re-login.** A user belonging to two workspaces switches via a UI control that updates `sessions.active_workspace_id`. The middleware reads that column to set the GUC; switching workspaces does not rotate the session token, which means a security event affecting one workspace does not necessarily invalidate the user's sessions elsewhere — only an explicit revoke or expiry does.
- **Email is the user identity.** Changing email requires a verification link to the new address and a confirmation link to the old, both consumed before the change applies. Documented in the runbook (`docs/auth.md`) when that lands.
- **Residual threat: phishing for magic-links.** Mitigations are short token lifetime (15 minutes), single-use consumption, a "this was sent because someone entered your email at plinth.farulivan.com — if that was not you, ignore this email" line in the message body, and a Permissions-Policy + framing-headers posture inherited from the Norven security model so the link's landing page cannot be embedded in a phishing chrome.
