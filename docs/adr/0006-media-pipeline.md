# Media pipeline: Sharp at upload, content-addressed S3, Cloudflare CDN delivery

Image uploads are processed at upload time, not at publish time. The dashboard accepts a multipart upload, validates the bytes, computes a content hash, and runs the stream through Sharp to emit responsive AVIF + WebP variants at four widths plus a JPEG fallback. Variants land in `s3://plinth-media/tenants/{workspace_id}/{content_hash}/w{width}.{format}` and the media library row stores the metadata. The publish-time Astro build (see [ADR-0003](./0003-publish-pipeline.md)) references those CDN URLs directly — Sharp does not run again. I chose this shape because processing once at upload time bounds the per-image cost at upload (not at every publish), because content-addressed paths give automatic deduplication when a tenant re-uploads the same hero photo to two sections, and because the same Sharp toolchain proved itself on Norven's build-time photo processing — the pipeline is one library, two trigger points.

## Considered options

- **Sharp at upload + content-addressed S3 + Cloudflare CDN** (chosen) — process once, serve from S3 behind Cloudflare, identical CDN URL shape in preview and production.
- **Cloudflare Images (managed)** — rejected for MVP. Cleaner ops (no Sharp infra), automatic variant generation, ~$5/mo per 100k images delivered, but couples the media layer to Cloudflare's pricing curve and gives up the lower-level practice of designing the variant pipeline directly. Worth revisiting if upload volume ever justifies the per-image cost (north of ~5000 uploads/month aggregated); documented as a migration path.
- **Imgix / imagekit.io / Bunny Optimizer (URL-parameter transforms)** — rejected. Defers the cost to per-request transformation; introduces a third-party in the rendering path; serves a different URL per variant per request, which fights HTTP cache hit rates. Worse architecturally than pre-computed variants for a portfolio-traffic profile.
- **Astro `astro:assets` at publish time only** — rejected. Works for Norven where photos sit beside the markdown at repo build time; does not fit a CMS where uploads happen at runtime. Re-running Sharp on every publish would also be wasteful when the same image is re-published across many tenant publishes.
- **On-the-fly Sharp via serverless function** — rejected. Generates variants on first request; cold-start latency, cache miss cost, and the editor would see uploaded images delayed by a multi-hundred-millisecond serverless invocation. Wrong UX for the editor flow, where "upload and see it immediately" is the property that matters.

## Consequences

- **The upload flow** is one synchronous request from the editor's perspective. The dashboard POSTs to `/api/media/upload`; the server validates MIME via magic-byte sniffing (not just extension), enforces a 20 MB upper bound, computes a SHA-256 of the bytes, and checks for an existing media row keyed by `(workspace_id, content_hash)` — returning the existing row on hit. On miss, the bytes stream through Sharp's pipeline emitting AVIF + WebP + JPEG at widths `[400, 800, 1200, 1600]`, the variants upload to S3 at content-hashed paths, and a `media` row is inserted with `{workspace_id, content_hash, width, height, file_size, content_type}`.
- **Storage layout** is `s3://plinth-media/tenants/{workspace_id}/{content_hash}/w{width}.{format}`. Content-addressed paths mean the same image uploaded twice produces one storage write and one media row — automatic deduplication per tenant. Cross-tenant deduplication is deliberately not attempted; isolation per [ADR-0002](./0002-tenant-isolation.md) wins over storage savings every time.
- **Variant widths `[400, 800, 1200, 1600]` mirror Norven's `<Frame>` widths verbatim.** The renderer emits a `<picture>` with `<source type="image/avif">`, `<source type="image/webp">`, and an `<img>` JPEG fallback — same shape as Norven, same Lighthouse `image-delivery-insight` posture. A tenant whose layout needs a different width set declares the override at the template level (in `packages/template-*`), not in the upload pipeline.
- **Alt text lives on the field that references a media row, not on the media row itself.** Context matters: a hero image is "Coastal house at dusk" in the hero section and "Salt House — west facade" in a gallery caption. The Zod schema for any image-bearing field has `media_id` + `alt` as paired required keys — the renderer fails the build if `alt` is missing, matching Norven's schema-enforced a11y.
- **The `media` table is tenant-owned and RLS-scoped** per [ADR-0002](./0002-tenant-isolation.md). A media row's `workspace_id` is set from the GUC at insert; cross-tenant reads return empty even with a guessed `id`.
- **Public CDN URLs.** Every variant URL is publicly resolvable through Cloudflare's edge. Marketing site images are public anyway; the trade-off matches Norven's "all content intentionally public" posture from its hosting ADR. A draft's images are guessable only with the full SHA-256 content hash; the dashboard never leaks the hash to non-authenticated viewers and crawling random hashes is infeasible at that entropy.
- **Preview and production use the same CDN URL.** The `resolveImageUrl()` helper from [ADR-0007](./0007-preview-architecture.md) is a kept seam — currently both modes resolve to the same shape; the seam is reserved for a future signed-URL gate (e.g., if a workspace ever wants its drafts gated behind authentication). Document the seam as "presently identity, deliberate", not removed — the moment a tenant asks for private previews, the seam is already in place.
- **Orphaned uploads** — a media row whose `id` is not referenced by any field in any `content_drafts` or `content_versions` row, older than 7 days, is swept by a daily Inngest reaper. The reaper deletes the row and the S3 variants in one transaction; this is the only place in the codebase where S3 `DeleteObject` is issued, so a regression there cannot silently leave orphaned blobs uncleaned.
- **Image processing is synchronous from the editor's perspective.** The upload endpoint blocks until the variants land in S3; the editor sees the new media in the library within the request lifetime. Variant generation for a 4000×3000 photo runs ~600 ms; the budget for the upload endpoint is 5 seconds (long enough for a 20 MB photo at slow network speeds), with a Honeycomb alert at chronic 3-second latencies. Async processing was considered but rejected — the editor UX of "uploaded but still processing" is worse than the editor UX of "wait 800 ms" for the file sizes this CMS targets.
- **Per-tenant storage cap** is enforced at upload time by summing `file_size` on the `media` table — 5 GB on free tier, 50 GB on paid. Exceeding the cap returns 413 with an instructive UI message. The sum is RLS-scoped so the cap is per-workspace and cannot accidentally include another tenant's bytes.
- **Per-tenant upload rate cap** is 100 uploads per hour per workspace, enforced by Upstash Redis. Same posture as the publish cap in [ADR-0003](./0003-publish-pipeline.md); the Redis dependency is documented once across both ADRs.
- **Sharp runs on the dashboard runtime** — Fly.io or Railway, both of which support native libvips bundling. The deploy target choice is documented as a constraint here so the deploy ADR cannot propose an environment where Sharp will not run (Vercel Edge runtimes will not host libvips; Vercel Node functions will, but with cold-start cost for the upload endpoint).
- **Audit log records uploads** — `workspace_id`, `actor_user_id`, `media_id`, `content_hash`, `file_size`, source IP — but does not record the bytes themselves. Reading the audit log is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **Trade-off accepted: variant generation at upload time means a schema change adding a fifth width** (e.g., `2400 px` for retina-XL) requires backfilling the variant for every existing media row. Documented as the operational toil this pipeline introduces; a re-encoder Inngest job that walks the `media` table and produces missing variants is the standard fix when that day comes. The trade is "no work at publish, occasional bulk work at format-set evolution" — acceptable because format-set evolution is years apart, publishes are minutes apart.
