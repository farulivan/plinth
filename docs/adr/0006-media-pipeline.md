# Media pipeline: Sharp at upload on apps/api, content-addressed R2, Cloudflare CDN delivery

Image uploads are processed at upload time, not at publish time. The api (`apps/api`) accepts a multipart upload from the dashboard, validates the bytes, computes a content hash, and runs the stream through Sharp to emit responsive AVIF + WebP variants at four widths plus a JPEG fallback. Variants land in Cloudflare R2 at `r2://plinth-media/tenants/{workspace_id}/{content_hash}/w{width}.{format}` and the media library row stores the metadata. The publish-time Astro build (see [ADR-0003](./0003-publish-pipeline.md)) references those CDN URLs directly — Sharp does not run again. I chose this shape because processing once at upload time bounds the per-image cost at upload (not at every publish), because content-addressed paths give automatic deduplication when a tenant re-uploads the same hero photo to two sections, and because the same Sharp toolchain proved itself on Norven's build-time photo processing — the pipeline is one library, two trigger points.

## Considered options

- **Sharp at upload + content-addressed Cloudflare R2 + Cloudflare CDN** (chosen) — process once, serve from R2 directly through the Cloudflare CDN with zero egress fees, identical CDN URL shape in preview and production.
- **AWS S3 + CloudFront** — rejected. Per-GB egress at ~$0.09/GB is the dominant cost line for media-heavy tenant sites and would blow the portfolio-budget posture as soon as one tenant's hero image is hot-linked. Requires a separate AWS identity outside the Cloudflare account and a CloudFront layer to match what R2 + Cloudflare give natively in one bind. R2's zero egress fees and same-account Workers/CDN bindings make it the strictly cheaper, simpler fit for this stack's scale.
- **Cloudflare Images (managed)** — rejected for MVP. Cleaner ops (no Sharp infra), automatic variant generation, ~$5/mo per 100k images delivered, but couples the media layer to Cloudflare's pricing curve and gives up the lower-level practice of designing the variant pipeline directly. Worth revisiting if upload volume ever justifies the per-image cost (north of ~5000 uploads/month aggregated); documented as a migration path.
- **Imgix / imagekit.io / Bunny Optimizer (URL-parameter transforms)** — rejected. Defers the cost to per-request transformation; introduces a third-party in the rendering path; serves a different URL per variant per request, which fights HTTP cache hit rates. Worse architecturally than pre-computed variants for a portfolio-traffic profile.
- **Astro `astro:assets` at publish time only** — rejected. Works for Norven where photos sit beside the markdown at repo build time; does not fit a CMS where uploads happen at runtime. Re-running Sharp on every publish would also be wasteful when the same image is re-published across many tenant publishes.
- **On-the-fly Sharp via serverless function** — rejected. Generates variants on first request; cold-start latency, cache miss cost, and the editor would see uploaded images delayed by a multi-hundred-millisecond serverless invocation. Wrong UX for the editor flow, where "upload and see it immediately" is the property that matters.

## Consequences

- **The upload flow** is one synchronous request from the editor's perspective. The dashboard forwards the multipart payload to the api's `/media/upload` route; the api validates MIME via magic-byte sniffing (not just extension), enforces a 20 MB upper bound, computes a SHA-256 of the bytes, and checks for an existing media row keyed by `(workspace_id, content_hash)` — returning the existing row on hit. On miss, the bytes stream through Sharp's pipeline emitting AVIF + WebP + JPEG at widths `[400, 800, 1200, 1600]`, the variants upload to R2 at content-hashed paths via the S3-compatible API, and a `media` row is inserted with `{workspace_id, content_hash, width, height, file_size, content_type}`.
- **Storage layout** is `r2://plinth-media/tenants/{workspace_id}/{content_hash}/w{width}.{format}`. Content-addressed paths mean the same image uploaded twice produces one storage write and one media row — automatic deduplication per tenant. Cross-tenant deduplication is deliberately not attempted; isolation per [ADR-0002](./0002-tenant-isolation.md) wins over storage savings every time.
- **Variant widths `[400, 800, 1200, 1600]` mirror Norven's `<Frame>` widths verbatim.** The renderer emits a `<picture>` with `<source type="image/avif">`, `<source type="image/webp">`, and an `<img>` JPEG fallback — same shape as Norven, same Lighthouse `image-delivery-insight` posture. A tenant whose layout needs a different width set declares the override at the template level (in `packages/template-*`), not in the upload pipeline.
- **Alt text lives on the field that references a media row, not on the media row itself.** Context matters: a hero image is "Coastal house at dusk" in the hero section and "Salt House — west facade" in a gallery caption. The Zod schema for any image-bearing field has `media_id` + `alt` as paired required keys — the renderer fails the build if `alt` is missing, matching Norven's schema-enforced a11y.
- **The `media` table is tenant-owned and RLS-scoped** per [ADR-0002](./0002-tenant-isolation.md). A media row's `workspace_id` is set from the GUC at insert; cross-tenant reads return empty even with a guessed `id`.
- **Public CDN URLs.** Every variant URL is publicly resolvable through Cloudflare's edge. Marketing site images are public anyway; the trade-off matches Norven's "all content intentionally public" posture from its hosting ADR. A draft's images are guessable only with the full SHA-256 content hash; the dashboard never leaks the hash to non-authenticated viewers and crawling random hashes is infeasible at that entropy.
- **Preview and production use the same CDN URL.** The `resolveImageUrl()` helper from [ADR-0007](./0007-preview-architecture.md) is a kept seam — currently both modes resolve to the same shape; the seam is reserved for a future signed-URL gate (e.g., if a workspace ever wants its drafts gated behind authentication). Document the seam as "presently identity, deliberate", not removed — the moment a tenant asks for private previews, the seam is already in place.
- **Orphaned uploads** — a media row whose `id` is not referenced by any field in any `content_drafts` or `content_versions` row, older than 7 days, is swept by a daily Inngest reaper. The reaper deletes the row and the R2 variants in one transaction; this is the only place in the codebase where R2 `DeleteObject` is issued, so a regression there cannot silently leave orphaned blobs uncleaned.
- **Image processing is synchronous from the editor's perspective.** The upload endpoint blocks until the variants land in R2; the editor sees the new media in the library within the request lifetime. Variant generation for a 4000×3000 photo runs ~600 ms; the budget for the upload endpoint is 5 seconds (long enough for a 20 MB photo at slow network speeds), with a Sentry performance alert at chronic 3-second latencies. Async processing was considered but rejected — the editor UX of "uploaded but still processing" is worse than the editor UX of "wait 800 ms" for the file sizes this CMS targets.
- **Per-tenant storage cap** is enforced at upload time by summing `file_size` on the `media` table — 5 GB on free tier, 50 GB on paid. Exceeding the cap returns 413 with an instructive UI message. The sum is RLS-scoped so the cap is per-workspace and cannot accidentally include another tenant's bytes.
- **Per-tenant upload rate cap** is 100 uploads per hour per workspace, enforced by Upstash Redis. Same posture as the publish cap in [ADR-0003](./0003-publish-pipeline.md); the Redis dependency is documented once across both ADRs.
- **Sharp runs on the api runtime (`apps/api`)** — Fly.io machines built on a Debian base bundle libvips natively, and the runtime split per [ADR-0008](./0008-repo-and-runtime-topology.md) keeps Sharp's ~600 ms CPU pulse off the dashboard's request handlers (the original reason for splitting the two apps). The deploy target choice is documented as a constraint here so the deploy ADR cannot propose an environment where Sharp will not run (Vercel Edge runtimes will not host libvips; Cloudflare Workers will not either, which is why uploads stay on Fly.io even though the rest of the Hono surface could run on Workers).
- **Audit log records uploads** — `workspace_id`, `actor_user_id`, `media_id`, `content_hash`, `file_size`, source IP — but does not record the bytes themselves. Reading the audit log is RLS-scoped per [ADR-0002](./0002-tenant-isolation.md).
- **Trade-off accepted: variant generation at upload time means a schema change adding a fifth width** (e.g., `2400 px` for retina-XL) requires backfilling the variant for every existing media row. Documented as the operational toil this pipeline introduces; a re-encoder Inngest job that walks the `media` table and produces missing variants is the standard fix when that day comes. The trade is "no work at publish, occasional bulk work at format-set evolution" — acceptable because format-set evolution is years apart, publishes are minutes apart.

**Amendment: the width set grew, and a reference now records its own.** The final trade-off above predicted this day and was wrong about one thing — it assumed the toil was the backfill. It was not. The backfill was merely expensive; what made adding a width unshippable was that the renderer derived its `srcset` by calling `mediaVariantWidths(originalWidth)`, a pure function of the constant. Editing the constant therefore changed what *every* reference advertised, retroactively, including references sitting inside snapshots published months earlier whose R2 objects were written under the old set and cannot grow. The failure would not have waited for the backfill to finish; it would have been immediate, one 404 per image per new width, on pages nobody was rebuilding.

The fix is to make the reference self-describing, the same property `contentHash` already gives it. `mediaRef.widths` records which variants were generated; absent means the reference predates the recording and falls back to `LEGACY_MEDIA_VARIANT_WIDTHS`, a frozen copy of `[400, 800, 1200, 1600]` kept as a separate constant so that editing the live one cannot silently edit history. A null `variant_widths` column reads the same way, which matters more than it looks: an 800 px original already has everything today's rule would produce, and treating null as "nothing" would re-encode it into byte-identical objects.

Widths are now `[400, 800, 1200, 1366, 1600, 1920]`. 1366 is the one that was blocking a gate — Lighthouse desktop emulates a 1350 px viewport at DPR 1, so a `sizes="100vw"` hero jumping 1200 → 1600 handed the browser 30,385 bytes it never painted and failed `uses-responsive-images` against a `maxLength: 0` assertion. With 1366 present the audit reports zero wasted bytes and the tenant categories sit at 1.0 across performance, accessibility, best-practices and SEO.

**Original bytes are now retained** at `tenants/{ws}/{hash}/original.{ext}`, and this is the correction the earlier trade-off needed most: without them the re-encoder it proposed was not merely unbuilt, it was unbuildable. A w1920 cannot be made from a w1600 without upscaling. The original is never served — the worker's `MEDIA_PATH` and the api's `variantParam` both validate the filename against `w{digits}.{format}`, which matters more here than for variants because the original still carries the camera's EXIF, GPS included, where Sharp's re-encode drops it. It shares the content-addressed prefix, so the orphan reaper's prefix delete sweeps it unchanged.

Every image uploaded before this amendment is permanently on the legacy four. There is nothing to decode, so the nightly re-encoder skips those rows rather than retrying them, and their references already claim exactly the set that exists. The remedy, where an author wants the wider set on an old image, is to re-upload the file: dedupe now short-circuits only while the existing variants are current, and otherwise encodes the missing widths and returns the widened item, which the picker writes back into the field. That is the only path that fixes both halves at once.

**The known gap: a re-encode widens objects, not references.** Because a reference freezes its widths at pick time, media the nightly job converges does not change any page until the image is re-picked. This is the deliberate cost of self-renderable snapshots — the alternative, rewriting references inside every tenant's draft on a schedule, would mutate content on a cron and surface as "unpublished changes" appearing unbidden. Re-upload covers the case an author actually cares about; a bulk reference migration, if it is ever wanted, belongs in the playbook at `docs/migrations.md` rather than in a background job.

**Measured cost** on the 6240×3510 hero (4.9 MB JPEG): 12 objects in 1,017 ms and 0.8 MB before, 18 objects in 1,786 ms and 1.7 MB after. The 5-second upload budget above holds with room; the earlier "~600 ms" figure describes the four-width era and is superseded. Storage per image rises by roughly the variant increase plus the retained original, and the per-tenant cap is unchanged — it sums `file_size`, which counts the original only, so the cap was already an undercount of true R2 usage and is now a smaller one. Making it count derived bytes is a product decision, deliberately not folded into this amendment.
